## Проверка, что профилирование не влияет на числа

Одной командой выполнить два независимых smoke-прогона и сравнить
все численные значения и базовые траектории (счётчики при этом могут различаться):

```powershell
.\CHECK_RESEARCH_V3.ps1 -ArbacRoot 'C:\Users\DLR_ACER\Desktop\arbac-Magister' -Workers 8
```

Повторно использовать два каталога проверки можно только при неизменном коде,
иначе механизм защиты сообщит о несовместимости манифестов.
Обычные эксперименты и профилированные эксперименты запускать в разных каталогах.
Профилирование существенно влияет на время — время для статьи надо считать **отдельно**.

## Единицы и точность счётчиков

`op_add`: вызовы `backend.add/sub`; `op_mul`: `mul`; `op_div`: `div`;
`op_neg`: `neg`; `op_special`: `pow/sqrt/log/exp/...`.
`op_total` — сумма этих категорий. Счётчик фиксирует **вызовы API** только в
`accelerator.step`, не внутренние арифметические операции `mpmath`/Arb,
не вызовы из генератора базового ряда и не программно-аппаратные инструкции.
Код, вызывающий функции `mpmath` напрямую, может не отражаться в этих счётчиках.

`step_elapsed_ms` — время внутри `accelerator.step`. Обычное `elapsed_ms` —
время более широкого расчёта до подготовки исходной траектории анализа.
Профилирование добавляет накладные расходы. **Для статьи время замерять с
выключенным профилированием**, профили операций проводить отдельно.

Ни один `cpp_*` показатель не подменяется новыми счётчиками. C++ имеет
свой независимый инструментарий. Формулы оценок ошибок оставлены без изменения.

## Сверка последних алгоритмов

Список известных регистраторов на GitHub (без исполнения Python-кода):

```powershell
python -m arbac_research audit `
  --base 'C:\Users\DLR_ACER\Desktop\arbac-Magister' `
  --json .\out\arbacc_base_audit.json
```

Когда последняя непрокоммиченная версия библиотеки будет доступна в папке
`C:\Users\DLR_ACER\Desktop\Arbac-LATEST`, сравни её так:

```powershell
python -m arbac_research audit `
  --base 'C:\Users\DLR_ACER\Desktop\arbac-Magister' `
  --candidate 'C:\Users\DLR_ACER\Desktop\Arbac-LATEST' `
  --json .\out\arbacc_migration_diff.json
```

Это **статическое сравнение файлов и зарегистрированных имён**,
оно не доказывает математическую корректность алгоритмов. До интеграции
все изменённые методы требуют smoke-регрессий с эталонами и проверки
пограничных случаев. `git commit`/`git push` эта поставка не выполняет.

## Совместимость и сохранность

- `out/research_smoke` и любые старые Parquet остаются доступными для `analyze`/GUI.
- При новом `run` изменившийся код/конфиг обнаруживаются по SHA256; возобновление чужого прогона **запрещено**, чтобы не смешивать данные.
- `summary.parquet` считается кэшем и пересчитывается при смене схемы метрик.
- `NULL` означает отсутствие сведений, особенно для старых файлов и счётчиков без профилирования.
- Ошибки и неуспешные шаги сохраняются с номерами использованных членов в event-строках.

## Подготовить непрокоммиченные исходники для интеграции

Чтобы не включать многогигабайтные `out` и Parquet, можно упаковать только
исходные файлы, тесты, JSON и документацию:

```powershell
.\PACK_LOCAL_ARBAC.ps1 -RepoRoot 'C:\Users\DLR_ACER\Desktop\arbac-Magister' `
  -OutputZip .\ARBAC_LOCAL_SOURCE_FOR_REVIEW.zip
```

Для этой задачи важнее всего архив **самой последней локальной версии**
алгоритмов, а не повторное архивирование GitHub-копии от 1 ноября.
После сверки исходников можно сделать отдельный branch/commit с алгоритмами,
отдельный с профилированием и независимым GUI, затем прогнать полную регрессию.
