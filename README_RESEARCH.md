# Arbac Research v2 — JSON → ZSTD Parquet → независимый GUI

**Обновление от 11.11.2026:** расширенные метрики и GUI в `README_V2.md`.
Для установки v2 поверх предыдущей версии используй этот файл.

**Назначение:** исследовательский модуль для существующего Python-проекта `arbacc`.
Разработан как **добавляемый пакет**, чтобы не перезаписывать непрокоммиченную
локальную версию библиотеки. Репозиторий `Magister` сверялся по GitHub (1 ноября 2026),
но эту версию следует отдельно проверить на последних локальных исходниках.

## Установка (Windows / PowerShell)

Скопируйте каталог `arbac_research` в корень вашей рабочей папки Arbac
**рядом с `arbacc`**. Не заменяйте существующие файлы библиотеки. Установите
зависимости в той среде Python, где запускаете Arbac:

```powershell
python -m pip install -r requirements-research.txt
python -m pytest research_tests/test_research_metrics.py research_tests/test_research_storage.py -q
```

Для полного набора тестов Arbac отдельно запустите его штатные тесты.

## 1. JSON и прямой расчёт в Parquet

Используется **тот же** JSON-формат, что у `python -m arbacc.cli run`.
Входы с `postprocess` и `envelopes` пока явно отклоняются, чтобы не потерять
результаты без предупреждения. Поддерживаются источники (series/sequence),
алгоритмы и точности, зарегистрированные в **вашей** Arbac.

```powershell
python -m arbac_research run examples/research_smoke.json --output out/research_smoke --workers 8 --chunk-tasks 32
```

Файлы в каталоге:

```
out/research_smoke/
  manifest.json               # отпечаток конфига + версии исходников
  config.json                 # конфигурация расчёта
  trace/
    part-<hash>.parquet       # ZSTD с полными траекториями
  summary.parquet             # быстрый автономный просмотр в GUI
```

Результат каждой группы задач сохраняется атомарно непосредственно в Parquet.
При повторном запуске с тем же конфигом готовые части пропускаются; повреждённые
неполные `.tmp` не считаются готовыми. **Нельзя менять `--chunk-tasks`, код или
конфигурацию и продолжать в той же папке.** Для новой версии используйте новый каталог.

**Запуск без дорогого набора (проверка интеграции):**

```powershell
python -m arbac_research run examples/research_smoke.json --output out/research_smoke --workers 1 --max-tasks 1
```

**Для полного прогона** уберите `--max-tasks` и используйте отдельный каталог.

Методам не нужно пересчитывать исходную последовательность при анализе —
каждый Parquet содержит значения исходной последовательности на каждом `m`
и все доступные корректные результаты преобразования.

## 2. Независимый анализ на основе Parquet

```powershell
python -m arbac_research inspect out/research_smoke
python -m arbac_research analyze out/research_smoke --epsilon 1e-8 --group accel_id,backend,dps --task-csv out/tasks.csv --group-csv out/summary.csv --summary-parquet out/research_smoke/summary.parquet
python -m arbac_research analyze out/research_smoke --epsilon 1e-30 --group class_id,accel_id
```

При смене ε **не запускаются алгоритмы**: перечитываются только сохранённые
траектории. Для исследования с 100 dps значения записываются текстом (без
потерь через float64). Ошибки и выигрыши вычисляются через mpmath с запасом
точности. При делении на 0 выигрыш может быть бесконечным; 0/0 даёт `null`.

### Метрики

- `best_error`, `best_n`, `last_error`, `last_n` — ошибка на лучшем (oracle)
  и последнем корректном приближении; **oracle нельзя использовать онлайн**.
- `gain_best_orders`, `gain_last_orders` — `log10(err_base(m)/err_acc(m))`.
  Разные числа использованных членов **не сравниваются**.
- `c1`, `c5` — индикаторы G≥1 и G≥5 по задаче. Группировка по умолчанию
  **не** считает один тест десятки раз при переборе параметров: для каждого
  `(series_id,noise_id)` выбирается лучшая конфигурация ретроспективно, затем
  считаются числа успешных последовательностей; `--per-task` отключает эту
  дедупликацию. В статье это следует называть oracle best configuration.
- `base_first_epsilon_n`, `accel_first_epsilon_n`, `epsilon_saved_terms` —
  раннее достижение порога и экономия членов, если обе стороны достигли порога.
- `last_best_loss_orders` — потеря точности от лучшего к последнему шагу.
- `relative_error_best`, `sign_changes`, `error_increases`, `error_decreases`.
- `status`, `failure`, `elapsed_ms` — отдельный учёт отказов и времени.

**Если исходная траектория отсутствует** (старый Parquet), G/C1/C5 остаются
неизвестными. Это важнее, чем получить красивое, но некорректное число.

### Метрики старого C++-проекта

Рассмотрены исходники `shanks-university/Magister`, в частности
`AlgoRankingTable.model.ts` и `convergenceUtils.ts`:
минимальная/последняя ошибка, шаг до ε, экономия шагов, число смен знака,
монотонность, выигрыши по порядкам, деления на ноль, метрики сложности,
рейтинг, параметры постобработки. В исследовательский модуль входят ключевые
сопоставимые численные метрики; **точный учёт количества арифметических
операций, события фильтров и C++-рейтинг пока не перенесены**. Их нельзя
восстановить из Паркет без соответствующих событий и счётчиков в источнике.

## 3. Отдельный GUI (без Arbac для анализа)

```powershell
python -m arbac_research gui
python -m arbac_research gui out/research_smoke
```

Вкладки независимы:

1. **Запуск из JSON**: выбрать конфиг, каталог, число процессов; кнопка «Запустить».
2. **Анализ Parquet**: выбрать готовую папку или Parquet-файл с совместимой схемой;
   выбрать ε, группировку, получить таблицу; открыть график по отдельной задаче;
   экспортировать CSV.

GUI анализа запускается и **без пакета `arbacc`**: нужны только `arbac_research`,
mpmath, pyarrow, matplotlib, стандартный Tkinter.

Для произвольного внешнего Parquet можно передать JSON-сопоставление колонок:

```json
{"task_id":"case_id","n_used":"m","value":"estimate","exact_sum":"limit","accel_id":"algorithm"}
```

```powershell
python -m arbac_research analyze external.parquet --mapping mapping.json
```

Parquet должен содержать понятные поля задачи, номера потреблённых членов и
приближения. **Совсем произвольную таблицу без соответствия колонок невозможно
интерпретировать как эксперимент ускорения сходимости.**

## 4. Прежние результаты Arbac

В GitHub `Magister` уже есть `all_iterations.parquet` и `all_results.parquet`.
Их можно нормализовать, не вычисляя алгоритмы повторно:

```powershell
python -m arbac_research convert-legacy out/old/all_iterations.parquet out/old/all_results.parquet --output out/converted_trace
python -m arbac_research gui out/converted_trace
```

**Ограничение**: исходная последовательность в старых двух таблицах обычно
не записывалась рядом с каждым шагом алгоритма. Из `all_iterations` одной лишь
базовой ошибки при том же числе членов не получить; не следует придумывать G.
Если исходные ряды и конфигурация сохранились, можно дополнить их отдельным
этапом без повторного запуска алгоритмов.

## 5. Что важно сделать до коммита

- Сверить с последними локальными `arbacc` и архивами исследований; Github версия
  устарела относительно локальной.
- Выполнить 1-2 небольших интеграционных JSON-прогона на Windows.
- Проверить числа и статусы против сохранённых Stage C/E и набора аналитических
  эталонов; измерить объём и выигрыш скорости на реальных данных.
- После проверки включить модуль в `Magister`, покрыть стабильным CI.

Без этих проверок **коммит в удалённый репозиторий не следует считать готовым**.

## Одна PowerShell-команда для полного запуска

```powershell
.\RUN_RESEARCH_FULL.ps1 -Config .\examples\research_smoke.json -Output .\out\research_smoke -Workers 8 -RunTests
```

Для реального полного эксперимента замените конфигурацию на свой большой JSON,
а каталог на новый (например, `out/research_full`). В нём **не должно быть**
`postprocess`/`envelopes` для `research v1`. `--max-tasks` в полном прогоне
не используется. Параметры `research.epsilon`, `research.baseline_budget` и
`research.class_by_series_id` добавлены только для исследовательского слоя;
базовая библиотека Arbac их игнорирует.

Отдельная сверка метрик с C++ и нашим тезисом: `METRICS_REVIEW.md`.

### Точность и состав результатов

`baseline_budget` управляет числом исходных членов, сохраняемых для независимого
анализа (не больше `n_max` алгоритма, но не меньше максимального `n_used`).
Измеренное `elapsed_ms` — время непосредственно вычисления ускорителя до
подготовки базовой траектории и сжатия Parquet. Значение нулевой наблюдаемой
ошибки означает совпадение **при сохранённой точности**, а не математическое
доказательство точного достижения предела.

GUI использует `summary.parquet` как кеш, если все Parquet-части старше кеша
и порог ε совпадает. Поэтому большой результат можно открыть значительно
быстрее, чем пересчитывать аналитику для каждого открытия.
