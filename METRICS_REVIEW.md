# Метрики Arbac / Shanks C++ / тезиса

Проверены исходники `DarkLordRowan/shanks-university`, ветка `Magister`:

- `frontend/web/frontend/src/widgets/AlgoRankingTable.model.ts`
- `frontend/web/frontend/src/widgets/AlgorithmSeriesConvergenceTable/model/convergenceUtils.ts`
- `frontend/web/frontend/src/widgets/SeriesComputedConvergenceTable/model/seriesComputedConvergenceUtils.ts`

Сравнивать **только одни и те же числа использованных исходных членов m** —
важное требование для основной исследовательской метрики. В C++-рейтинге
есть не только такая метрика, но и другая, относительно наилучшего
исходного приближения независимо от m. Их не нужно смешивать.

| Что | Показатель | Реализовано v1 |
|---|---|---|
| Главный показатель нашего тезиса | `gain_best_orders = log10(error_base(m*)/error_acc(m*))` | Да, при известном S и исходной траектории |
| Выигрыш на последнем шаге | `gain_last_orders` | Да |
| Доля тестовых последовательностей с G≥1, G≥5 | `C1`, `C5` | Да; агрегат по уникальным тестам с best-configuration oracle |
| Лучшая ошибка и её шаг | `best_error`, `best_n` | Да (ретроспективно) |
| Последняя ошибка и её шаг | `last_error`, `last_n` | Да |
| Потеря от лучшего к последнему | `last_best_loss_orders` | Да |
| Время достижения epsilon и выигранные члены | `base_first_epsilon_n`, `accel_first_epsilon_n`, `epsilon_saved_terms` | Да при сохранённой базовой траектории до общего бюджета |
| Аналог C++ `ordersGains` (другая метрика!) | `cpp_orders_gain_vs_series_min` | Да, на сохранённом диапазоне исходных членов |
| Аналог C++ `relativeErrors` | `cpp_relative_error_vs_series_min` | Да |
| C++ амплификация при минимуме ускорителя | `ampAtMinNGains` | Близкий аналог — `gain_best_orders`, где n=m использованных членов |
| C++ односторонность, смены знака | `one_sided`, `sign_changes` | Да для вещественных величин |
| C++ монотонность ошибки | `error_increases`, `error_decreases` | Да как количественные признаки |
| Отказ алгоритма, деление на ноль | `status`, `division_zero_failure` | Да на уровне статуса/ошибки, но без номера первой ошибки и восстановления |
| Сложность и число арифметических операций | `complexityFormula`, profiling | Нет; нужна инструментализация по шагам |
| События фильтрации и восстановление после ошибок | `filterTrigger*`, `divZeroRecovered*` | Нет; нужны события и отдельные траектории постобработки |
| C++ суммарный рейтинг | `totalRankScore` | Не переносим как основной научный критерий: агрегированная эвристика скрывает компромиссы |

## Раздельные уровни успеха

- **Факт улучшения**: `G > 0` при равном m; недостаточно для C1.
- **C1**: `G >= 1`, то есть ошибка уменьшилась хотя бы в 10 раз.
- **C5**: `G >= 5`, то есть ошибка уменьшилась хотя бы в 100000 раз.
- **Скорость достижения точности**: первое `m`, где ошибка `< epsilon`.
- **Устойчивость**: доля отказов, деления на ноль, неудачи по классам;
  нужно смотреть отдельно по `float64`, `mpmath`, `Arb` и параметрам.
- **Неправильный предел**: нельзя признать по конечной траектории автоматически;
  требуется специальная аналитически определённая семья тестов.

## Важная оговорка об агрегировании

Если один метод испытан с 50 параметрами на одной и той же последовательности,
это **одна последовательность, а не 50 независимых успехов**. По умолчанию
агрегатор выбирает максимальный `G` из конфигураций для каждого
`(series_id, noise_id)` и считает C1/C5 по уникальным тестам. Это
**оракульный подбор параметра по известному пределу**, а не оценка качества
практического алгоритма выбора параметров.

Для исследовательского анализа каждого прогона по отдельности используйте
`--per-task`, для предсказательной оценке эффективности понадобится отбор
параметров на независимых последовательностях или группах.

## Требования к статьям

Сохранять результаты отдельно для: (1) best-step oracle, (2) last valid,
(3) first-to-epsilon, (4) failures, (5) online stopping (если реализован).
Не смешивать `ordersGains` из C++ с нашим `G_j` и не называть десятичные
порядки напрямую «верными десятичными цифрами» без оговорок.

## Обновление v2 (11 ноября 2026)

Вместо короткой таблицы введены категории для *всех вычислимых из v1 trace*
метрик. В GUI есть динамическая полная таблица, паспорт отдельной задачи
и словарь определений. В CSV сохраняются все поля, включая значения
высокой точности текстом. В разделе `README_V2.md` — точные команды.

- **Сравнение на равном бюджете**: наш `gain_best_orders`, `gain_last_orders`,
  статистики по каждому шагу и доля шагов с улучшением.
- **Сопоставление с C++**: `cpp_orders_gain_vs_series_min`,
  `cpp_relative_error_vs_series_min`, `cpp_amp_at_best_n_orders`,
  `cpp_step_series_amp_{mean,median,worst}_orders`.
- **Конечная точность и отказы**: число корректных и невалидных шагов,
  классификация отказов, число увеличений ошибки, доля увеличений,
  изменения знака и монотонность траектории.
- **Порог**: отдельные индикаторы успеха, времени достижения epsilon,
  экономии входных членов и различия между C1/C5 и достижением ε.
- **Групповая аналитика**: C1/C5, доли, покрытие, отказы, медиана/среднее,
  минимум/максимум и P5/P95 выигрыша, статистики по времени.

**Тонкости соответствия C++:** в оригинале `computeOrdersGain` при нулевой
ошибке использует специальную конечную величину. Эту договорённость мы
сохраняем только в отдельных `cpp_*` полях. В оригинале имеется
`almostEqual` с допуском для классификации равных ошибок; в наших
научных метриках сравнение сохраняет арифметику высокой точности без
произвольного допуска. Точные числовые результаты в особых вырожденных
случаях поэтому не обязаны совпадать с веб-рейтинговой эвристикой.

**Неперенесённые показатели:** счётчики арифметических операций, момент
первого события деления на ноль и последующее восстановление, а также
включение/срабатывание фильтров. Это задача инструментирования runner,
а не функции постобработки сохранённых Parquet v1.
